File: `src/lib/validation.ts`

Purpose and responsibilities: Defines server-side Zod schemas and nickname helpers for registration, administration, SOLENIZANT, The Floor, SPORT, Jaka to melodia?, and Pojedynki actions.

Important exports, inputs, and outputs: The Floor configuration accepts distinct `teamAId` and `teamBId`; bets accept `targetTeamId`; result confirmation accepts `winnerTeamId`. SPORT setup permits a pair-only confirmation with an empty rank list, or a complete ranking in which every submitted active player is ranked exactly once. Ranks are consecutive from 1 through the submitted team size and are not capped at five. SPORT bets, winners, four limb requirements, and bounded bonus points have focused schemas. All use the fixed team-ID schema.

Dependencies: Zod, team constants, and SOLENIZANT metadata.

Backend/database interactions: None. Route Handlers pass parsed data to `database.ts`.

Implementation details: SPORT validation rejects reused pair teams, duplicate ranks, duplicate player assignments, and gaps in a rank sequence before the database repeats authoritative stage, roster-membership, active-player, and full-roster checks. The bonus schema always carries all four stable teams.

Player-removal correction: `playerIdSchema` accepts only a positive safe integer, plus its canonical positive-decimal string representation for an in-flight browser snapshot generated before the BIGSERIAL parsing correction. It never accepts decimal, signed, whitespace-padded, boolean, or arbitrary-string identifiers.

Future expansion: Keep every sensitive endpoint on a narrow, focused schema.

Segment V accepts exactly the four distinct fixed team IDs for setup, a positive safe song identifier for song and final-result actions, and a stable team ID for tie resolution and settlement approval. Song scores accept artist/title correctness, 0–5 singing lines, a mistake flag, and optional lyric-auction declarations with unique participants and a declared winner.

Segment VI update: `activeSegmentSchema` includes `pojedynki`. Its focused configuration schema accepts exactly two different fixed team IDs; player bets and administrator result confirmation each accept only a team ID. The database repeats all phase, eligibility, membership, and balance checks.

Segment VIII adds `familiada` navigation and `familiadaActionSchema`. Its UUID revision and discriminated command schema accept four distinct team IDs for setup, validated player IDs for selecting representatives or overriding priority, a bounded answer position, or a fixed team ID for a bet or result. The database resolves stage, roles' applicable state, match membership and position bounds for the question.

FINAŁ adds `finale` navigation and `finaleActionSchema`. The request carries a UUID revision and either an ordered, distinct finalist pair, a non-negative decimal string, a fixed direction or finalist ID, or a phase progression command. The schema normalizes comma and dot decimals to numbers. The server state machine checks the estimate unit, qualification, phase and winner eligibility.

`alkoholicyActionSchema` validates the four distinct performance teams, a distinct duel pair, 0–6 charades scores, non-negative integer duel points, fixed two-game market numbers and bounded commands. `goldActionSchema` validates two to four distinct participating teams and safe player IDs for nominee, representative or winner commands. Both use a UUID revision and fixed segment navigation IDs. The database checks the persisted phase and actual membership.
