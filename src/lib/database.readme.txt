File: `src/lib/database.ts`

Purpose and responsibilities: Owns all Neon PostgreSQL access, schema bootstrap/migration, sessions, player data, SOLENIZANT scoring, The Floor team duels/bets/settlement, SPORT challenges/bonuses, Jaka to melodia? scoring/bets, Pojedynki duels/bets/settlement, and administrator actions.

Important exports, inputs, and outputs: Focused The Floor helpers start the segment, configure two teams, record a team bet, lock betting, advance team turns, finish a timed duel, confirm a winning team, settle bets once, and open the next slot. SPORT helpers persist two administrator-selected pairs and a complete ranking for every active player, seed/advance eight challenges, accept and settle bets, and configure/score two all-team bonus rounds.

Dependencies: Node `crypto`, Neon, `server-only`, constants, Floor metadata, SOLENIZANT metadata, and shared types.

Backend/database interactions: SPORT adds `sport_pairings`, `sport_player_numbers`, `sport_challenges`, `sport_bets`, `sport_chip_transfers`, `sport_bonus_rounds`, and `sport_bonus_requirements`, plus independent SPORT stage/current-sequence columns on `game_state`. The `sport_player_numbers` migration removes the former upper limit of five and retains only a positive-rank constraint, preserving existing assignments. The Floor migration adds durable team-side, active-team, team-clock, winner-team, and bet-target-team columns. It backfills them from legacy player references without touching player balances, teams, or scores. Legacy player columns remain solely for safe historical compatibility.

Implementation details: SPORT pairs always contain all four teams exactly once. The administrator can persist pairs first without replacing prior rankings; a non-empty rank submission must then include every active roster member exactly once with a unique, consecutive rank from 1 through the team's size. The fixed schedule still uses only ranks 1–5, so starting challenges additionally requires at least five correctly ranked active players in every team. The chosen pair slot controls each fixed challenge; no team ID is hardcoded in its schedule. A SPORT bet is accepted only from an active player outside both competing teams and debits exactly 2 chips. Settlement is one SQL statement guarded by `settled_at`: a correct bettor receives stake plus 2 profit funded equally (with deterministic four-place remainder) by active members of the losing competing team; incorrect stakes are distributed equally to active members of the winning team. Transfer rows provide the durable ledger. SPORT bonuses only update team scores, never player chips.

Player-removal correction: `defaults.parseInt8` is enabled at this server-only persistence boundary because Neon otherwise returns PostgreSQL `BIGSERIAL`/`int8` identifiers as text while shared contracts deliberately use safe JavaScript numbers. `deactivatePlayer` remains one atomic SQL statement: it marks the player inactive, revokes matching opaque sessions, and records the admin action while retaining chips, bets, transactions, rankings, and completed history. Active roster and betting checks already filter by `players.active`, so removal takes effect immediately in every game phase without deleting a team or historical row.

Future expansion: Use focused service functions and versioned migrations as the schema grows; never expose generic SQL to route or UI layers.

Segment VI update: `game_state` has independent `pojedynki_stage` and current sequence columns. `pojedynki_duels` stores exactly four pending/betting/live/result slots, their two different selected team IDs, winner, timestamps, and durable `settled_at`; `pojedynki_bets` holds exactly one fixed 2-chip wager from each eligible player per duel. The focused services seed slots, configure teams, debit authorized remaining-team bets, require all eligible bets before live state, save one competing winner, settle the closed pot once, advance only through Duel 4, and refund only pending stakes during restart.
