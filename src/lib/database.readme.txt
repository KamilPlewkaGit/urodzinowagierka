File: `src/lib/database.ts`

Purpose and responsibilities: Owns all Neon PostgreSQL access, schema bootstrap/migration, sessions, player data, SOLENIZANT scoring, The Floor team duels/bets/settlement, SPORT challenges/bonuses, Jaka to melodia? scoring/reward settlement, Pojedynki duels/bets/settlement, and administrator actions.

Important exports, inputs, and outputs: Focused The Floor helpers start the segment, configure two teams, record a team bet, lock betting, advance team turns, finish a timed duel, confirm a winning team, settle bets once, and open the next slot. SPORT helpers persist two administrator-selected pairs and a complete ranking for every active player, seed/advance eight challenges, accept and settle bets, and configure/score two all-team bonus rounds.

Dependencies: Node `crypto`, Neon, `server-only`, constants, Floor metadata, SOLENIZANT metadata, and shared types.

Backend/database interactions: SPORT adds `sport_pairings`, `sport_player_numbers`, `sport_challenges`, `sport_bets`, `sport_chip_transfers`, `sport_bonus_rounds`, and `sport_bonus_requirements`, plus independent SPORT stage/current-sequence columns on `game_state`. The `sport_player_numbers` migration removes the former upper limit of five and retains only a positive-rank constraint, preserving existing assignments. The Floor migration adds durable team-side, active-team, team-clock, winner-team, and bet-target-team columns. It backfills them from legacy player references without touching player balances, teams, or scores. Legacy player columns remain solely for safe historical compatibility.

Implementation details: SPORT pairs always contain all four teams exactly once. The administrator can persist pairs first without replacing prior rankings; a non-empty rank submission must then include every active roster member exactly once with a unique, consecutive rank from 1 through the team's size. The fixed schedule still uses only ranks 1–5, so starting challenges additionally requires at least five correctly ranked active players in every team. The chosen pair slot controls each fixed challenge; no team ID is hardcoded in its schedule. A SPORT bet is accepted only from an active player outside both competing teams and debits exactly 2 chips. Settlement is one SQL statement guarded by `settled_at`: a correct bettor receives stake plus 2 profit funded equally (with deterministic four-place remainder) by active members of the losing competing team; incorrect stakes are distributed equally to active members of the winning team. Transfer rows provide the durable ledger. SPORT bonuses only update team scores, never player chips.

Player-removal correction: `defaults.parseInt8` is enabled at this server-only persistence boundary because Neon otherwise returns PostgreSQL `BIGSERIAL`/`int8` identifiers as text while shared contracts deliberately use safe JavaScript numbers. `deactivatePlayer` remains one atomic SQL statement: it marks the player inactive, revokes matching opaque sessions, and records the admin action while retaining chips, bets, transactions, rankings, and completed history. Active roster and betting checks already filter by `players.active`, so removal takes effect immediately in every game phase without deleting a team or historical row.

Optional betting: The Floor, SPORT, and Pojedynki accept the verified administrator's start action with any number of eligible bets, including zero. The server closes betting at the stage transition and settles only submitted bets.

Future expansion: Use focused service functions and versioned migrations as the schema grows; never expose generic SQL to route or UI layers.

Segment V uses its own five song slots, lyric-auction declarations, team totals, and game stage. Confirming the fixed teams persists the ready stage. Start opens song one atomically. Scoring awards up to 7 points across recognition and singing, and the fifth score opens final results. The administrator selects a tied leader when necessary and confirms settlement separately. PostgreSQL validates the current winner and active roster, calculates exact four-decimal allocations, and records previous balances, new balances and deltas in melodia_chip_transfers. The game and player locks, unique final-song/player key and settlement timestamp protect concurrent requests. A blocked settlement changes no balance. Restart reverses this segment's points and preserves completed transfers and their audit rows. Legacy bootstrap refunds pending historical debits once and keeps previously settled finals as completed.

Snapshot reads use one read-only repeatable-read transaction so stages, balances, scores, and the settlement ledger describe the same point in time.

Segment VI update: `game_state` has independent `pojedynki_stage` and current sequence columns. `pojedynki_duels` stores exactly four pending/betting/live/result slots, their two different selected team IDs, winner, timestamps, and durable `settled_at`; `pojedynki_bets` holds at most one fixed 2-chip wager per eligible player per duel. The focused services seed slots, configure teams, debit authorized remaining-team bets, close betting at the administrator's start request, save one competing winner, settle the closed pot once, advance only through Duel 4, and refund only pending stakes during restart. The winner call may safely retry the same durable un-settled result after an interrupted request, but can never switch a winner or resettle. Like The Floor, a no-correct-bet result refunds the fixed stakes; four-decimal rounding residue is assigned deterministically to the earliest correct bet.

SPORT audit entries give setup and bonus result parameters explicit PostgreSQL types inside their JSON constructors. The challenge-start guard requires four distinct team positions across the two saved pairs before it moves the game and challenge zero into betting.

Pojedynki start types the fixed duel-count parameter explicitly in the PostgreSQL audit JSON constructor.

Segment VIII: `applyFamiliadaAction` takes a validated command with a UUID revision and, for player actions, a verified session player ID. `game_state.familiada_state` stores the two matches, full question sets, progress and scoring, with a changing `familiada_revision`. The shared game-row lock and conditional revision update serialize gameplay writes, including first buzzer acceptance. Selected player rows are locked to verify they are still active at commit. `familiada_bets` stores one two-chip wager per match and player. The SPORT stake, correct-bet profit and deterministic decimal remainder rules apply. Match confirmation, result, payout, team transfers and audit details commit together. Restart refunds pending stakes only and renews the revision. Full reset also clears the matches and wagers. The repeatable-read snapshot exposes only the viewer's wager and projects the current answer key only on explicit admin reads.
